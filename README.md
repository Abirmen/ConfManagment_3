# Ассемблер и интерпретатор учебной виртуальной машины (УВМ)

**Дисциплина:** Конфигурационное управление  
**Практическая работа:** №3  
**Вариант:** №2  
**Язык реализации:** Python 3 (стандартная библиотека)  
**Интерфейс:** параметры командной строки (файл конфигурации не требуется)  
**Репозиторий:** <https://github.com/Abirmen/ConfManagment_3>

## Описание проекта

Проект представляет собой комплект консольных приложений для учебной
виртуальной машины (УВМ) варианта №2:

* **ассемблер** — читает текстовую программу в формате JSON, переводит её
  во внутреннее представление и кодирует в 5-байтовые машинные команды;
* **интерпретатор** — загружает двоичный файл, выполняет программу на
  модели УВМ и сохраняет дамп памяти данных в формате JSON.

Архитектура УВМ:

* гарвардская модель: память команд и память данных разделены;
* длина команды — 5 байт (40 бит), порядок байтов — little-endian;
* 64 регистра (адресация 6 бит), инициализируются нулями;
* память данных — массив 32-битных беззнаковых ячеек (65536 ячеек);
* операция `bitreverse()` выполняется над 32-битным беззнаковым целым:
  бит `i` переходит в бит `31 - i`.

## Спецификация УВМ и язык ассемблера (JSON)

### Таблица команд

| Мнемоника JSON | Код `A` | Поле `B` | Поле `C` | Поле `D` | Семантика |
| --- | --- | --- | --- | --- | --- |
| `load_const` | 35 | константа, 21 бит | адрес регистра, 6 бит | — | `regs[C] = B` |
| `read_mem` | 3 | адрес памяти, 12 бит | адрес регистра, 6 бит | — | `regs[C] = data_mem[B]` |
| `write_mem` | 122 | адрес регистра-источника, 6 бит | адрес регистра с адресом памяти, 6 бит | — | `data_mem[regs[C]] = regs[B]` |
| `bitreverse` | 110 | адрес регистра с базовым адресом, 6 бит | адрес памяти для результата, 12 бит | смещение, 14 бит | `data_mem[C] = bitreverse32(data_mem[regs[B] + D])` |

### Размещение полей в 40-битной команде

| Команда | Поле | Биты | Диапазон значений |
| --- | --- | --- | --- |
| `load_const` | `A` | 0–6 | 35 |
| `load_const` | `B` (константа) | 7–27 | 0…2097151 |
| `load_const` | `C` (регистр) | 28–33 | 0…63 |
| `read_mem` | `A` | 0–6 | 3 |
| `read_mem` | `B` (адрес памяти) | 7–18 | 0…4095 |
| `read_mem` | `C` (регистр) | 19–24 | 0…63 |
| `write_mem` | `A` | 0–6 | 122 |
| `write_mem` | `B` (регистр-источник) | 7–12 | 0…63 |
| `write_mem` | `C` (регистр с адресом) | 13–18 | 0…63 |
| `bitreverse` | `A` | 0–6 | 110 |
| `bitreverse` | `B` (базовый регистр) | 7–12 | 0…63 |
| `bitreverse` | `C` (адрес результата) | 13–24 | 0…4095 |
| `bitreverse` | `D` (смещение) | 25–38 | 0…16383 |

Биты, не занятые полями команды, заполняются нулями. Команда кодируется
в 5 байт в порядке little-endian (младший байт первым).

### Формат входного JSON-файла

Корневой элемент — объект с единственным обязательным ключом `program`,
значение которого — непустой массив команд. Каждая команда — объект
с ключом `op` (мнемоника) и обязательными полями этой мнемоники.
Необязательный ключ `comment` содержит произвольную строку-пояснение
и на трансляцию не влияет.

Пример `tests/spec_tests.json` — четыре контрольные команды
из методички:

```json
{
  "program": [
    {"op": "load_const", "const": 557, "reg": 45},
    {"op": "read_mem", "addr": 623, "reg": 34},
    {"op": "write_mem", "src_reg": 23, "addr_reg": 29},
    {"op": "bitreverse", "base_reg": 53, "dst_addr": 639, "offset": 905}
  ]
}
```

Поля мнемоник:

| Мнемоника | Обязательные поля | Диапазоны |
| --- | --- | --- |
| `load_const` | `const`, `reg` | `0 <= const <= 2097151`, `0 <= reg <= 63` |
| `read_mem` | `addr`, `reg` | `0 <= addr <= 4095`, `0 <= reg <= 63` |
| `write_mem` | `src_reg`, `addr_reg` | `0 <= src_reg <= 63`, `0 <= addr_reg <= 63` |
| `bitreverse` | `base_reg`, `dst_addr`, `offset` | `0 <= base_reg <= 63`, `0 <= dst_addr <= 4095`, `0 <= offset <= 16383` |

Любое нарушение схемы (неизвестная мнемоника, отсутствующее или лишнее
поле, неверный тип, выход за битовый диапазон) приводит к сообщению
в `stderr` с кодом ошибки и кодом возврата 1.

## Параметры командной строки

### Ассемблер (`src/assembler.py`)

| Флаг | Обязательный | Назначение |
| --- | --- | --- |
| `-i`, `--input` | да | путь к JSON-файлу с текстом программы |
| `-o`, `--output` | да | путь к двоичному файлу с машинным кодом |
| `-t`, `--test` | нет | вывести машинный код на экран в байтовом виде |

### Интерпретатор (`src/interpreter.py`)

| Флаг | Обязательный | Назначение |
| --- | --- | --- |
| `-i`, `--input` | да | путь к двоичному файлу с машинным кодом |
| `-o`, `--output` | да | путь к JSON-файлу для дампа памяти данных |
| `-r`, `--range` | нет (по умолчанию `0:31`) | диапазон дампа в формате `START:END` |

## Архитектура и реализованные этапы

### Этап 1. Промежуточное представление (ассемблер, часть 1)

* `src/spec.py` — константы УВМ и неизменяемые описания команд
  (`OperandSpec`, `CommandSpec`); все коды операций, сдвиги и разрядности
  заданы именованными константами.
* `src/errors.py` — класс `UvmError` с машиночитаемым кодом и каталог
  кодов ошибок.
* `src/instruction.py` — dataclass `Instruction`: внутреннее представление
  команды (описание команды и упорядоченные значения полей), форматирование
  в виде `A=35, B=557, C=45`.
* `src/json_loader.py` — чтение JSON, проверка схемы документа и диапазонов,
  построение списка `Instruction`.
* `src/assembler.py` — CLI: разбор аргументов, загрузка программы и вывод
  полей в режиме `--test`.

В ветке `stage-1` файл `--output` содержал текстовый листинг IR;
начиная с этапа 2 в него записывается машинный код.

### Этап 2. Формирование машинного кода (ассемблер, часть 2)

* `src/encoder.py` — кодирование IR в 5-байтовые слова: код операции
  объединяется по ИЛИ со значениями полей, сдвинутыми на свои позиции,
  после чего слово переводится в 5 байт little-endian.
* `src/assembler.py` — запись байтового потока в `--output`, вывод размера
  файла и, в режиме `--test`, байтового представления каждой команды.

Контрольный прогон: 4 команды × 5 байт = 20 байт, побайтовое совпадение
со всеми четырьмя тестами методички.

### Этап 3. Интерпретатор и операции с памятью

* `src/memory.py` — классы `DataMemory` (65536 ячеек по 32 бита с маской
  `0xFFFFFFFF`) и `RegisterFile` (64 регистра); оба класса проверяют
  границы и сообщают об ошибке `E11`.
* `src/decoder.py` — разбор байтового потока на 5-байтовые слова
  little-endian, декодирование в `Instruction`, проверка кратности длины
  файла 5 байтам (`E09`), известности кода операции (`E10`) и нулевого
  значения неиспользуемых битов (`E14`).
* `src/uvm.py` — `ProgramMemory` (память команд) и `VirtualMachine`:
  цикл интерпретации со счётчиком команд, диспетчеризация обработчиков
  через словарь, операции `load_const`, `read_mem`, `write_mem`.
* `src/interpreter.py` — CLI: загрузка бинарного файла, выполнение,
  разбор диапазона `START:END` с проверкой границ и запись JSON-дампа.

Структура JSON-дампа памяти:

```json
{
  "range": {"start": 0, "end": 19},
  "memory_size": 65536,
  "program_size": 30,
  "executed_instructions": 30,
  "cells": {"0": 11, "1": 22, "...": "..."}
}
```

Пример `tests/copy_array.json` записывает массив `[11, 22, 33, 44, 55]`
в адреса `0..4`, затем читает его и копирует в адреса `10..14`.

### Этап 4. Арифметико-логическое устройство

* `src/alu.py` — функция `bitreverse_32(value)`: побитовый разворот
  32-битного беззнакового целого (маска `0xFFFFFFFF`), бит `i` переходит
  в бит `31 - i`.
* `src/uvm.py` — обработчик команды `bitreverse` (`A=110`): вычисляет
  эффективный адрес `regs[B] + D`, читает ячейку, применяет
  `bitreverse_32` и записывает результат по адресу `C`; обе операции
  с памятью проверяют границы.
* `tests/test_bitreverse.json` — записывает 6 значений в адреса
  `110..115`, загружает базовый адрес `100` в регистр `5` и применяет
  `bitreverse` со смещениями `D = 10..15`, сохраняя результаты
  в адреса `200..205`.

### Этап 5. Тестовая задача и три примера программ

Тестовая задача варианта №2 — поэлементно применить `bitreverse()`
к вектору длины 8 и записать результат в новый вектор. Реализованы три
программы с различными данными:

* `tests/task_vector8_case1.json` — степени двойки и базовые числа
  `[1, 2, 4, 8, 15, 16, 255, 1024]`, исходный вектор в `100..107`,
  новый — в `200..207`;
* `tests/task_vector8_case2.json` — граничные и палиндромные значения
  `[0, 1, 3, 5, 170, 255, 65535, 1048575]`, исходный вектор в `100..107`,
  новый — в `200..207`;
* `tests/task_vector8_case3.json` — смешанные данные
  `[4096, 65535, 1048575, 1, 123456, 654321, 777, 2024]`, база `50`
  и смещения `D = 10..17` (исходный вектор в `60..67`), новый вектор
  в `300..307`; дополнительно результат `300` повторно разворачивается
  в ячейку `400` для проверки инволютивности.

Все три программы ассемблируются, исполняются и проверяются сквозными
тестами `tests/test_task_examples.py` (сверка каждого из 8 элементов
с независимой эталонной реализацией разворота битов).

## Коды ошибок приложения

| Код | Причина |
| --- | --- |
| `E01` | Некорректные аргументы командной строки |
| `E02` | Ошибка чтения входного файла |
| `E03` | Синтаксическая ошибка JSON |
| `E04` | Нарушение схемы документа (лишние ключи, пустая программа) |
| `E05` | Неизвестная мнемоника команды |
| `E06` | Отсутствует обязательное поле команды |
| `E07` | Неверный тип значения поля |
| `E08` | Значение поля вне допустимого битового диапазона |
| `E09` | Некорректная длина двоичного файла |
| `E10` | Неизвестный код операции при декодировании |
| `E11` | Выход за границы памяти данных или регистров |
| `E12` | Ошибка записи выходного файла |
| `E13` | Некорректный диапазон адресов дампа |
| `E14` | Ненулевые неиспользуемые биты команды |

## Запуск через PowerShell

Команды `run.sh` дублирует `tests/run.ps1`: он запускает ассемблер,
интерпретатор, тесты и демонстрацию, сам создаёт каталог `output/`
и включает кодировку UTF-8.

```powershell
.\tests\run.ps1 assemble  tests\spec_tests.json output\spec_tests.bin -Test
.\tests\run.ps1 interpret output\copy_array.bin output\copy_array.dump.json -Range 0:19
.\tests\run.ps1 test
.\tests\run.ps1 demo
```

Демонстрационные сценарии этапов: `tests/test_stage1.ps1` … `tests/test_stage5.ps1`.

## Тестирование

Полный прогон модульных и сквозных тестов:

```bash
python -m unittest discover -s tests -v
```

или через скрипт запуска:

```bash
./run.sh test
```

Результат последнего реального прогона:

```text
Ran 55 tests in 0.110s

OK
```

Что покрыто тестами:

* `tests/test_encoder.py` — побайтовое кодирование четырёх команд
  и размер файла 20 байт;
* `tests/test_decoder.py` — обратимость кодирования, ошибки длины,
  неизвестного кода операции и ненулевых неиспользуемых битов;
* `tests/test_json_loader.py` — схема JSON и все коды ошибок разбора;
* `tests/test_memory.py` — память данных, регистры и границы;
* `tests/test_interpreter.py` — копирование массива, структура дампа,
  диапазоны и ошибки загрузки;
* `tests/test_alu.py` — математическая точность `bitreverse_32`,
  включая инволютивность и отбрасывание старших битов;
* `tests/test_bitreverse.py` и `tests/test_task_examples.py` — сквозные
  прогоны всех примеров, включая три программы тестовой задачи;
* `tests/test_compliance.py` (совместно с `tests/audit_rules.py`) —
  автоматический аудит оформления: размер файлов и строк, длина
  и число параметров функций, цикломатическая сложность, docstrings,
  отсутствие комментариев, числовые литералы в сравнениях, имена PEP 8.

Демонстрация всех примеров одной командой (результаты складываются
в игнорируемый каталог `output/`):

```bash
./run.sh demo
```

## Работа с Git

История разработки ведётся отдельными коммитами по спецификации
Conventional Commits: каждый этап зафиксирован отдельной веткой
`stage-N`, а ветка `main` содержит итоговое состояние проекта.

```bash
git branch -a
git log --oneline --all --graph
```

| Ветка | Содержание этапа |
| --- | --- |
| `stage-1` | разбор JSON и внутреннее представление команд |
| `stage-2` | кодирование в 5-байтовый машинный код |
| `stage-3` | интерпретатор, память и JSON-дамп |
| `stage-4` | АЛУ и команда `bitreverse` |
| `stage-5` | три программы тестовой задачи над вектором длины 8 |

Формат сообщений коммитов: `feat: Этап N. Краткое название`
(например, `feat: Этап 3. Интерпретатор и операции с памятью`).
История состоит из пяти коммитов — по одному на каждый этап; ветки
`stage-1` … `stage-5` указывают на соответствующие коммиты.

Репозиторий опубликован на GitHub:
<https://github.com/Abirmen/ConfManagment_3>.
